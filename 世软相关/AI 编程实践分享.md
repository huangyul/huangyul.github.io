# AI 编程实践分享：通过 Skill 打造项目级 AI 开发助手

大家好，今天分享一下我在日常开发过程中使用 AI 编程的一些实践。

现在很多人使用 AI 编程，基本方式都是：

> 提一个需求，让 AI 生成代码。

这种方式确实可以提升效率，但是实际开发中会遇到很多问题：

比如：

- AI 不理解当前项目架构，经常生成不符合项目规范的代码
- AI 不知道历史代码设计，很容易修改出问题
- AI 写完代码以后，没有测试保障
- 遇到线上问题，只能让 AI 根据一小段报错猜原因

所以我目前的一个思路是：

> 不要只把 AI 当成代码生成工具，而是通过 Skill 给 AI 补充项目经验、开发规范和处理流程，让 AI 更像一个熟悉项目的工程师。

今天主要分享我目前使用比较多的 4 个 Skill。

---

# 一、什么是 Skill？

简单理解：

Skill 就是一份给 AI 的“工作手册”。

里面可以定义：

- 项目的背景信息
- 技术规范
- 开发流程
- 排查问题的方法
- 常见坑点

普通 AI：

```
需求
 ↓
AI 自己理解
 ↓
生成代码
```

容易出现：

```
不了解项目
不知道规范
不知道历史问题
生成质量不稳定
```

加入 Skill 后：

```
需求
 ↓
读取 Skill
 ↓
理解项目规则
 ↓
按照规范开发
 ↓
自动验证
```

AI 的输出质量会稳定很多。

---

# 二、Skill 1：开发指引 Skill

第一个 Skill 是开发指引。

这个 Skill 主要解决一个问题：

> 降低 AI 理解项目的成本。

大家知道，大型项目里面代码量非常大。

如果每次让 AI 开发一个功能，都让它重新阅读：

- 项目目录
- 技术架构
- 数据库设计
- 前后端规范
- 开发注意事项

不仅速度慢，而且会消耗大量 Token。

所以我把这些内容提前整理成一个开发导航。

比如：

项目采用 Monorepo 架构：

```
apps/web       前端 React + TypeScript
apps/server    后端 Go + Gin + GORM
shared         公共资源
```

后端统一遵循：

```
Handler
   ↓
Service
   ↓
Repository
   ↓
DB
```

AI 在开发新接口之前，就知道：

- Handler 不应该写业务逻辑
- Repository 只负责数据库操作
- Service 负责业务流程


同时里面也约束 AI 的代码输出方式：

比如：

- 先解释方案
- 给出目录结构
- 输出完整代码
- 标明修改文件
- 不允许 TODO 占位代码

这样可以避免 AI 生成一些看起来能运行，但是不符合项目规范的代码。

---

# 三、Skill 2：Go Test Skill

第二个 Skill 是 Go 测试规范。

这个主要解决：

> AI 写完代码以后，如何保证不会影响原有功能。

很多时候 AI 写代码很快，但是最大的问题是：

不知道它有没有改坏东西。

所以我把测试规范沉淀到了 Skill。

这个 Skill 不只是告诉 AI：

“帮我写测试”。

而是定义了一整套测试流程。


比如 E2E 测试：

不是简单调用接口：

```
请求接口
 ↓
判断 HTTP 200
```

而是完整验证：

```
创建测试环境

↓

执行接口

↓

验证返回结果

↓

验证数据库状态

↓

清理测试数据
```


测试过程中：

不会使用开发数据库。

而是：

1. 动态创建测试数据库
2. 执行 migration
3. 初始化测试数据
4. 执行业务流程
5. 删除测试数据库


这样避免：

测试污染开发环境。


同时要求 AI 测试覆盖：

- 正常流程
- 参数错误
- 权限问题
- 重复提交
- 数据一致性
- 并发风险


比如订单接口：

不仅测试：

```
创建订单成功
```

还需要考虑：

```
库存不足怎么办？

重复提交订单怎么办？

数据库状态是否正确？

权限是否校验？
```


这样 AI 生成的不只是测试代码，而是一套风险检查。

# 四、Skill 3：开发新报表 Skill

第三个 Skill 是一个业务型 Skill。

这个是我觉得效果比较明显的一个场景。

因为公司的报表开发通常比较复杂。

一个新报表不是简单写一个页面。

通常包含：

- 查询条件
- 多个 Tab 页
- 表格配置
- 分页
- 排序
- 导出
- 多语言
- 路由注册


如果每次开发，都让 AI 自己摸索：

效率会很低。


所以我把完整开发流程整理成 Skill。


里面定义：

第一步：

分析需求和 API 文档。


需要提取：

- 模块名称
- 查询条件
- 子表数量
- 字段结构
- 接口地址


第二步：

按照模板生成页面。


比如：

主页面：

```
index.vue
```

子表：

```
components/
    Store.vue
    Product.vue
```


同时约束一些容易踩坑的问题。


例如：

查询不要一次请求所有 Tab。

应该：

```
用户点击哪个 Tab

↓

只加载哪个 Tab 数据
```

避免无效接口压力。


再比如：

所有页面中文不能直接写：

错误：

```js
label: "销售金额"
```

正确：

```js
label: this.$t("sale_amount")
```


这些规范如果靠人工记忆，很容易遗漏。

但是放进 Skill 后：

AI 每次生成都会自动遵守。


这个 Skill 最大价值：

不是生成代码。

而是把一个开发流程固化下来。

# 五、Skill 4：日志排查 Skill

第四个 Skill 是问题排查。

这个主要解决：

> 让 AI 参与线上问题定位。

以前排查问题：

一般流程：

```
看到报错

↓

找日志

↓

猜原因

↓

修改代码

↓

验证
```


现在通过 Skill：

让 AI 按固定流程排查。


第一步：

根据错误信息提取：

- 接口地址
- request_id
- 时间
- 错误关键字


第二步：

自动提取对应日志。


第三步：

根据接口类型分类。


比如：

第三方接口：

```
微客云接口
```

重点检查：

- 请求参数
- 返回字段
- 字段类型


自研接口：

检查：

```
Handler

↓

Service

↓

Repository

↓

Database
```


第四步：

结合接口文档分析。


比如：

日志里面：

```
json unmarshal error
```

AI 会判断：

可能是：

```
第三方返回字段类型变化

↓

Go struct 类型不匹配

↓

修改 DTO
```


而不是直接告诉你：

“可能是 JSON 问题”。



这样 AI 的定位过程更接近人工工程师。

---

# 六、总结：Skill 带来的变化

总结一下，这几个 Skill 实际解决的是不同阶段的问题。


## 开发前

开发指引 Skill：

帮助 AI 快速理解项目。

降低：

- 阅读成本
- Token 消耗
- 设计偏差


---

## 开发中

业务 Skill：

把经验沉淀下来。

例如报表开发：

以前：

```
每次重新摸索
```

现在：

```
按照 SOP 自动执行
```


---

## 开发后

测试 Skill：

保证修改安全。

避免：

```
AI 改 A 功能

导致 B 功能挂掉
```


---

## 问题阶段

排查 Skill：

让 AI 从：

```
猜问题
```

变成：

```
按照流程分析问题
```


---

# 最后的思考

我认为未来 AI 编程的核心竞争力，不只是模型能力。

同样一个 GPT、Claude 或者其他模型：

如果只是直接聊天，效果有限。

但是如果给它：

- 项目知识
- 开发规范
- 流程经验
- 历史问题

它会变成一个更加稳定的工程助手。


所以未来开发人员的重要能力，可能不是单纯写代码。

而是：

> 如何把自己的工程经验沉淀成 AI 可以执行的规则，让 AI 放大自己的开发能力。
